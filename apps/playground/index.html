      Kontur DSL

      Experimenteller Syntaxumfang dieses Playgrounds. Das ist noch keine finale Kontur-Sprachspezifikation.

      Workspace und Schreibweise

      workspace "Name" { namespace "demo.beispiel" model { … } views { … } }

      In workspace { … } sind Name und innere Blöcke optional. model bookshop { … } ist eine Kurzform für einen Workspace mit Namespace bookshop und einem Modellblock. Schlüsselwörter unterscheiden Groß- und Kleinschreibung. IDs beginnen mit A–Z, a–z oder _ und können danach auch Ziffern und Bindestriche enthalten. Globale und qualifizierte Element-IDs sind workspaceweit eindeutig. Vorwärtsreferenzen sind möglich.

      Textwerte akzeptieren einen Bezeichner oder einfachen bzw. doppelten Anführungszeichen-Text. In Strings stehen \n und \t für Zeilenumbruch und Tabulator. Ein Backslash kann auch das nächste Zeichen maskieren. Kommentare beginnen mit #, // oder /* und enden bei der Blockform mit */. Semikolons sind innerhalb von Blöcken optional.

      Elemente und Hierarchie

      id = typ "Name" { … }

      Alternativ ist typ id "Name" { … } erlaubt. Direkt in model stehen system, actor, api, businessProcess, organization, team und person. In system stehen container, service und datastore. Letztere sind Container mit vorbelegtem kind. In Containern stehen component-Elemente. Elementblöcke sind optional und können auch Beziehungen enthalten.

      Ältere Modelle dürfen weiterhin den Workspace-Block organization { … } mit id = team "Name" und id = person "Name" verwenden. Deren optionale Blöcke akzeptieren dort description, email und url.

      Elementeigenschaften

      Textwerte folgen auf description, technology, protocol, style, interaction, lifecycle, kind, email oder url. external true markiert ein externes Element, external false setzt die Markierung zurück.

      contract openapi "./orders.yaml" speichert Format und Pfad. Der Playground liest die Datei nicht ein und warnt bei APIs ohne Vertragsreferenz.

      Verantwortlichkeiten und Quellen

      businessOwner anna businessOwner ben source "Zuständigkeitsliste" responsibilities { architect clara businessTeam commerce }

      productOwner, businessOwner, technicalOwner und architect erwarten person. businessTeam und technicalTeam erwarten team. Diese Rollen und die allgemeine Rolle owner sind direkt im Elementblock oder in responsibilities gültig. owner und frei benannte Rollen innerhalb von responsibilities akzeptieren person oder team.

      Jede Rolle kann beliebig oft mit je einer Ziel-ID deklariert werden. Personen und Teams werden unabhängig zugeordnet. Zugehörigkeit entsteht durch partOf. source ergänzt einen optionalen Herkunftshinweis. Bei Beziehungen steht er im Block, etwa { source "Betriebsvertrag" }.

      Event-APIs mit mehreren Topics

      events = api "Events" { produces "orders.created", "orders.cancelled" consumes "payments.settled" }

      Die beiden Listen beschreiben produzierte und konsumierte Topics aus Sicht des API-Anbieters. Listen können mehrfach angegeben werden und werden zusammengeführt. Topic-Namen mit Punkten brauchen Anführungszeichen.

      worker subscribes events { topics "orders.created" }

      topics ist bei publishes und subscribes optional und verweist auf deklarierte Topics dieser API. Ohne Auswahl bezieht sich die Beziehung auf die API als Ganzes.

      Beziehungen

      quellId beziehung zielId "Beschreibung" { … }

      Beschreibung in Anführungszeichen und Block sind optional. provides, consumes, publishes und subscribes verbinden System, Container oder Komponente mit einer API. Nur consumes akzeptiert { operations "listOrders", "createOrder" }. dependsOn zielt auf ein technisches Element. -> ist eine freie Beziehung. Setze Leerzeichen um den Pfeil.

      Organisation und Geschäftsprozesse

      partOf verbindet Organisation, Team oder Person mit einer Organisation oder einem Team. Mehrere Zugehörigkeiten sind möglich. developedBy, operatedBy, providedBy und customer verweisen auf Organisationen, Teams oder Personen. basedOn beschreibt eine Grundlage, supportedBy eine Unterstützung, etwa dispatch supportedBy shipping. Beide akzeptieren beliebige definierte Elemente. businessProcess beschreibt auch intern erbrachte Prozesse.

      Plattformen und technische API-Abhängigkeiten

      platform core "Core Platform" { productOwner anna capability messaging "Event Streaming" { technology "Kafka" } environment shared "Shared" }

      platform ist ein System mit eigenen Capabilities und Plattformumgebungen. Es unterstützt Systemeigenschaften wie lifecycle und mehrwertige Verantwortlichkeiten. capability und environment stehen in Plattformblöcken. Ihre qualifizierten IDs sind hier core.messaging und core.shared. Elementdeklarationen unterstützen beide Schreibweisen.

      api events "Order Events" { mode async usesCapability core.messaging topic created "orders.created" }

      APIs können im Modell oder in einem Systemblock stehen. Im System shop bekommt diese API die ID shop.events. Innerhalb des Systems ist auch events als Zielreferenz möglich. usesCapability kann je API beliebig oft stehen und akzeptiert eine Capability als Ziel. Optional folgt source "Hinweis". Dieselbe Beziehung kann auch als shop.events usesCapability core.messaging mit dem üblichen Beziehungsblock stehen.

      mode sync erlaubt provides und consumes. mode async erlaubt publishes und subscribes. Ohne Modus bleiben die bisherigen API-Beziehungen zulässig. topic benennt ein Topic im API-Block. orders publishes events.created nutzt im Systemblock die relative Topic-ID. Von außen lautet das Ziel shop.events.created. Die ältere topics-Schreibweise mit Topic-Namen bleibt gültig.

      Application Stages und Bindings

      stages dev, stage, prod bindings { shop.events@dev uses core.messaging@shared shop.events@prod uses core.messaging@production }

      stages steht im System- oder Plattformblock. bindings kann direkt im Workspace oder im Modell stehen. Ein Binding erwartet eine API, eine Stage ihres Systems, eine per usesCapability referenzierte Capability und eine Umgebung der anbietenden Plattform. Optional folgt source "Hinweis". Mehrere Stages und Anwendungen können dieselbe Umgebung nutzen. Mehrere passende Bindings werden angezeigt und behalten ihre Fundstellen.

      Der Stage-Selektor der technischen Sichten startet mit prod. Er verwendet ausschließlich passende Bindings aus den ausgewählten Repositories und zeigt bei fehlendem Binding „nicht spezifiziert“. Infrastruktur und Kubernetes-Deployments lassen sich über die Deployment DSL explizit modellieren.

      In den technischen Sichten zeigen durchgezogene Kanten deklarierte Interaktionen, Capability-Nutzung und Plattformzugehörigkeit. Gestrichelte Kanten in Platform Capabilities zeigen aus Service-Interaktion und Capability-Nutzung abgeleitete Abhängigkeiten. Sie werden nicht als Assertions gespeichert. Stages und technische Beziehungen werden additiv vereinigt. Identische Aussagen behalten alle Fundstellen, einschließlich der Fundstellen pro Binding.

      Sichten

      containers "Name" { scope systemId autoLayout lr include * }

      Typen sind landscape (auch systemLandscape), containers (auch container), components, apis (auch api), deployment, ownership, platformCapabilities und technicalDependencies. Name und Block sind optional. title setzt den Anzeigenamen. autoLayout oder layout akzeptiert lr, rl, tb oder bt, auch in Großbuchstaben. scope referenziert ein Element und filtert Container-, API- und technische Sichten. include * verwendet die Standardauswahl der Sicht. Die Oberfläche gruppiert Container-Sichten nach System und API-Sichten nach API. Für vorhandene Rollenzuordnungen ist eine Zuständigkeitssicht verfügbar.

      Deployment

      Deployment Environments stehen im model. Deployment Nodes können weitere Nodes, Infrastruktur und benannte Instanzen enthalten. Eine Instanz referenziert das logische Element. Technische Beziehungen zwischen logischen Systemen oder Containern werden auf ihre sichtbaren Instanzen übertragen.

      prod = deploymentEnvironment "Produktion" { cluster = deploymentNode "EKS" { ingress = infrastructureNode "Ingress" ns = deploymentNode "Namespace bookshop" { orderService = containerInstance orders shopInstance = softwareSystemInstance shop } } } prod.cluster runsIn core.production prod.cluster.ingress -> prod.cluster.ns.orderService "HTTPS"

      Deployment-Elemente werden mit ihrem vollständigen Pfad referenziert. runsIn verbindet einen Deployment Node mit einer Platform Environment. Im views-Block wählt environment die Topologie, stage die passenden API-Bindings. Optional beschränkt scope die Instanzen auf ein System oder eine Plattform.

      deployment "Bookshop · Produktion" { environment prod stage prod scope shop include * autoLayout lr }

      API-Interaktionen erscheinen an den beteiligten Instanzen. Die API führt zur genutzten Capability in der gebundenen Platform Environment. Fehlt für die gewählte Stage ein Binding, zeigt die Sicht die Capability mit „nicht spezifiziert“.

      Mehrere Quellmodelle

      Die zentrale Quellenauswahl gilt für alle Sichten. Repository, Revision und Quelldatei beschreiben die Herkunft des lokal editierten Modells. Standarddatei ist model.kontur. Identität entsteht aus namespace und Element-ID. Ohne Namespace teilen sich Quellen den leeren Namespace. Referenzen dürfen in einer anderen ausgewählten Quelle desselben Namespace definiert sein.

      Identische Aussagen über eine Beziehung oder Rolle erscheinen einmal, mit allen Fundstellen. Verschiedene Ziele derselben Rolle ergänzen sich. Fehlende Aussagen entfernen keine Zuordnungen. Unter ⓘ lassen sich Fundstellen und Reconciliation-Status per Klick oder Tippen aufrufen.

      Unbekannte Referenzen und falsche Zieltypen sind Validierungsfehler. Abweichende Werte in Feldern mit einem einzelnen Wert, etwa protocol, werden als Konflikt mit allen Varianten angezeigt. Das Diagramm nutzt für solche Felder den ersten Wert in Quellenreihenfolge. Topic-Listen werden vereinigt. Unvereinbare Elementtypen oder abweichende Parents blockieren die gemeinsame Vorschau. Eine Plattform kann ein System derselben Identität spezialisieren.
