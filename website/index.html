A vision for living software architecture

Architecture that knows when reality changes.

Your architecture evolves. Your documentation should, too.

Architecture models describe what you intend to build. Code, infrastructure, and running systems tell another part of the story. Kontur aims to connect them — so the differences become visible, understandable, and traceable.

01 / THE IDEA

Architecture isn't static.
Why should its documentation be?

Architecture diagrams often start as a good description of intent. Then teams ship features, infrastructure changes, and new integrations appear. The picture falls behind — even when everyone is doing their job.

Kontur explores a different approach: keep architectural intent in versioned source files, connect it to technical evidence, and make the gaps explicit. Not every gap is a problem. Every gap is an opportunity to understand what changed.

03 / DESIGN PRINCIPLES

Built for how teams actually work.

Kontur starts in the editor, not in a central diagram database. The model is yours, the files are yours, and the history lives in Git.

01

Source files are authoritative

Models live in Git. Previews, indexes and aggregate views are derived; proposed changes go through ordinary review.

02

Local-first, offline-capable

Describing and exploring a local architecture should require no account, central service or always-on connection.

03

Interfaces deserve identity

APIs are more than arrows between boxes. Kontur aims to treat contracts, ownership and lifecycle as architectural concepts.

04

Federated by design

Individual teams can own their models while a future consolidated view makes cross-team connections visible.

Local architecture modeling

  • Rust-based parser, semantic model and validation
  • Documented subset of Structurizr DSL
  • CLI for selecting and projecting a view
  • Live Mermaid preview in VS Code on Linux x64
  • Diagnostics and limited source navigation

Next and beyond

Architecture connected to evidence

  • Fuller local editing with language support and multi-file models
  • AI-assisted inspection and Git-reviewed changes
  • Cross-repository references and consolidated views
  • First-class API and ownership modeling
  • Source discovery and reconciliation with runtime evidence
These are directions, not released capabilities.
05 / ROADMAP

Grow from the editor outward.

Start with useful local tools. Then build bridges between teams and their systems.

  1. PHASE 01 · IN PROGRESS

    Local modeling

    Rust core, validation, CLI and IDE preview. More complete language support and workspace editing next.

  2. PHASE 02 · PLANNED

    Local AI assistance

    Inspect, reason about and propose model changes while keeping Git review in control.

  3. PHASE 03 · PLANNED

    Federated architecture

    Reference other teams' versioned models and understand the connections between them.

  4. FUTURE VISION

    Evidence and reconciliation

    Bring technical evidence into a consolidated view; show divergence with source traceability.
